## 0. 아키텍처 제약 (최우선 · 모든 구현이 이 안에서)

- **자체 서버 0.** Node/Python 상시 프로세스 없음. Supabase(BaaS)가 저장·SQL 필터·파기·로그·(추후)결제검증을 전담한다.
- **미수령 원칙.** 실명·원문·엔티티 매핑은 **사이트 서버로 전송되지 않는다.** 사이트는 라벨화된 결과(BLOCK B·C)만 수령한다.
- **클라이언트/서버 경계 (엄수):**
  - 프리스캔(regex 검사)·마스킹 미리보기 → **클라이언트 JS만.** 절대 Edge Function으로 빼지 않는다(실명이 함수로 전송되면 미수령 붕괴).
  - Edge Function은 **실명이 닿지 않는 작업**(결제 검증 등)에만.
- **전처리 위임.** 마스킹·라벨화는 사용자가 자신의 AI로 수행한다. 전처리 책임은 사용자(위탁자)에게 있다. 사이트는 2차 방어(접수 필터)만 수행한다.
- **진행바는 단일 공유 컴포넌트.** 스텝 배열 하나로 전 페이지가 갱신된다.
- **처리 3층 분리(§14 · IP 방어).** 유저 프롬프트(1단)엔 라벨화·마스킹·병합만. 서버 전처리(2단 정규화)·채점(3단 루브릭)은 프론트에 절대 내려가지 않는다. 1단 프롬프트도 복사 버튼 JS에 하드코딩하지 말고 Edge Function으로 발급(접수 세션 유저 한정). 서버 2단은 결정적 규칙+주석까지만 — 원문 텍스트를 AI로 재작성·교체 금지(재현성·근거추적·미수령 훼손).

## 2. 공유 컴포넌트 (먼저 구현·재사용)

### 2.1 ProgressBar
- 스텝 배열(통과 경로): `모델선택 › 이용동의 › 전처리 › 신청서 › 제출 › 자동검수 › 요금(스킵) › 접수 › 접수조회`
- props: `current`(현재 스텝 key), `rejected`(bool)
- 현재 스텝 = accent + bg-accent pill. 나머지 = muted.
- `rejected=true`: 자동검수 스텝을 danger로, 이후(요금·접수·조회) opacity 0.4.
- 통과: 자동검수를 ok색, 요금은 취소선(line-through, muted), 접수 강조.
- 스텝 추가/순서변경은 이 배열만 수정.

### 2.2 RejectCard (파기 카드)
- 입력: `code`, `standardText`, `detail?`(감지 유형 배열, 값·위치 미표시), `receiptNo`, `rejectedAt`
- 구성: 사유코드 배지(danger) + 표준문구 + (detail 있으면)유형 칩 + 파기기록 블록(접수번호/시각/코드/"원문 보존: 없음·파기됨") + "이 기록에 실명 없음" 주석.
- 7종 코드 공통 레이아웃. 코드별로 내용만 교체.

### 2.3 SubmitGate (제출 게이트)
- 3조건 AND → 버튼 활성:
  1. 본문·요약 파일 업로드됨 (BLOCK B·C · 비어있지 않음)
  2. 프리체크 통과 (식별자 4종 잔존 0 · BLOCK A 형태 미감지)
  3. 위탁자 보증 체크박스 on
- 미충족 시 버튼 disabled + `<i lock>` + 사유 라벨.

   - 클립보드 실패 대비 fallback(숨은 textarea select)
5. 하단: [이용동의] ← / [제출 단계로] →

**모델별:** 프롬프트 박스의 대상 프롬프트가 §7의 해당 모델본으로 교체.

### 3.2 신청서 페이지  `apply` (모델 차등)
**목적:** 분석 파라미터 입력. 공통골격 고정 + 모델 차등 교체.
- **공통골격:** 분석 범위(관찰 스코프 태그). (인물사전·시간축은 전처리로 이관됨 — 여기 없음)
- **LIT 차등:** 입장 선택(원고편/피고편/소외인편 · 다중·비혼합, 진영색 라디오) · 지칭 범위(상대만/자기서술 포함)
- **SNS 차등:** 플랫폼(SNS/메신저/발화) · 공인/사인 표시
- **SPK 차등:** 공인 게이트 확인 · 화자 동일성 · 변화 관찰창
- 하단 이전/다음.

### 3.3 제출 페이지  `submit`
**목적:** 전처리 AI 결과 수령(내부: BLOCK B·C). **붙여넣기 아님 — md 파일 업로드.**
**방식:** 전 구간 파일 방식으로 통일한다. AI가 낸 결과를 유저가 md 파일로 저장해 업로드하면, **브라우저(FileReader)에서** 프리체크·파싱한다. 통과분만 서버로. 원문 텍스트를 textarea에 붙여넣게 하지 않는다(길면 잘리고, 20개 규모에서 오류난다 — §13 근거와 동일).
**유저 대면 용어 규칙 (§13.6 준수):** 화면에 "BLOCK A/B/C" 전면 노출 금지. "AI가 정리한 결과 파일"로 부르고, 본문(B)·요약(C)으로 안내. BLOCK 표기는 괄호로만.
**요소:**
1. 선택 요약 배지(예: 피고편·소외인편) — 읽기전용
2. **본문 파일 업로드**(AI가 라벨화한 본문 md · 내부 BLOCK B) → FileReader → 프리체크(§4 regex) → "식별자 잔존 N" 배지
3. **요약 파일 업로드**(AI가 만든 익명 요약 md · 내부 BLOCK C) → FileReader → §4.4 파서 → 메타 카드:
   - 카드 4개: 서면수 · 엔티티(인물·계좌) · 시간축(확정/추정) · **표본축(모델별)**
   - 표본축: LIT=진영별(SAMPLE_DEPTH), SNS=대칭균형(SYMMETRY_BALANCE), SPK=시점별(DRIFT_WINDOW)
   - 편중 감지 시 warn 배너. **편중은 반려 아님(soft).** 한쪽 0건만 hard(§4.3).
   - 파싱 실패 시: "요약 파일 형식이 올바르지 않습니다. AI 출력을 그대로 저장해 올리세요."
   - **매핑표 파일 금지 안내**(내부 BLOCK A): "실명↔라벨 표는 올리지 마세요. 본인 기기에만 두세요. 실수로 올리면 자동 반려됩니다." 감지 시 반려.
   - AI 결과 파일명 규칙: 전처리 프롬프트가 결과를 `..._본문.md` `..._요약.md`로 저장하도록 안내(§7). 업로드 시 본문/요약 자동 판별 or 유저 지정.
4. 지칭 범위(LIT) — 신청서에서 안 받았으면 여기서. (위치는 신청서로 이동 가능 — 택1)
5. SubmitGate (§2.3) — 조건: 두 파일 업로드 + 프리체크 통과 + 위탁자 보증
6. 하단 이전 / [자동검수로 제출]

## 4. 마스킹 · 접수 필터 (2차 방어)

전처리(1차)는 사용자 AI가 수행. 사이트는 업로드된 md 파일을 **브라우저(FileReader)에서** 재검사한다(서버 미전송, 통과분만 전송).

### 4.1 하드 차단 regex 4종 (전 모델 · 잔존 시 파기)
```
주민등록번호/외국인등록번호  \d{6}-[1-4]\d{6}
전화                        01[0-9]-\d{3,4}-\d{4}
이메일                      [A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\.[A-Za-z]{2,}
사업자등록번호               \d{3}-\d{2}-\d{5}
```
추가 감지(경고/차단): 카드 `\d{4}-\d{4}-\d{4}-\d{4}`, 여권 `[A-Z]\d{8}`.

### 4.2 마스킹 3경로 (미리보기 표시 규칙)
- **자릿수 별표(구분자 유지):** 주민 13자리 전체(생년월일 포함) → `******-*******`, 전화 `***-****-****`, 사업자 `***-**-*****`, 카드 `****-****-****-****`, 이메일 `****@****.***`
- **인물 라벨:** 사람 이름은 별표 아님 → 지위 라벨(원고/피고N/소외인N…). 클라이언트는 잔존만 검사(사전은 사용자 측).
- **계좌 라벨:** 계좌는 별표 아님 → `[계좌X·은행명]`. 은행명 보존, 번호 전체 미노출, 소유자 결합 금지. **경고 티어**(오탐 대비, 하드차단 아님).

### 4.3 표본 균형 (전 모델 + 의견서 공통)
- **존재 = 하드.** 대칭/양측 중 한쪽 0건 → 반려(`한쪽0건`).
- **편중 = 소프트.** 얇으면 반려 안 함. 리포트 본문에 표본 두께 명시. **파일명에는 표기 안 함.**

### 4.4 BLOCK C 파서
모델별 키 추출(정규식 라인 파싱):
```
LIT: DOC_COMPOSITION / ENTITY_SCALE / TIMELINE_CONFIDENCE / SAMPLE_DEPTH / DROPPED_JUDGMENT
SNS: THREAD_COMPOSITION / SPEAKER_SCALE / TIMELINE_CONFIDENCE / SYMMETRY_BALANCE / DROPPED_JUDGMENT
SPK: UTTERANCE_COMPOSITION / SPEAKER_SCALE / TIMELINE_CONFIDENCE / DRIFT_WINDOW / DROPPED_JUDGMENT
```

### 4.5 접수 필터 모델별 실명 예외 (중요)
- **실명 잔존 허용:** SNS · Speaker (공인 실명 노출이 정당). 단 한글 인명 형태를 잔존으로 파기하지 **않음**.
- **실명 잔존 파기:** Litigation (전부 라벨화 원칙).
- **식별자(주민·전화·이메일·사업자·계좌 등) 잔존:** 전 모델 파기. (SNS·SPK도 식별자는 예외 없음)
- 구현: 필터에 `model` 파라미터 → LIT는 인명 NER 잔존도 파기 대상, SNS/SPK는 식별자 regex만.

### 4.6 파기 우선순위 (복수 사유 시 단일 회신, 제안·확정 전)
```
마스킹·개인정보미완 → 파일형식오류/파일내용없음 → 공인게이트불통과
 → 한쪽0건 → 출처불명 → 보관만료
```
앞 단계 걸리면 뒤 미검사. 판단요구는 파기 경로 아님(§5 비파기).

## 7. 전처리 프롬프트 3종 (전문 · 복사 버튼에 심음)

> 각 모델 전처리 페이지의 복사 버튼이 Edge Function으로 발급(§14.4, 하드코딩 금지). 화면에는 blur로만 노출.

> **중대 (§14 반영) — 이 프롬프트들은 "1단 단순화판"으로 개정 대상이다.** 아래 전문은 라벨화·마스킹·병합·비텍스트 치환까지만 유저에게 준다. 정규화·채점 관련 지시는 **제거**하고 서버 2·3단으로 옮긴다. 구체적으로 유저 프롬프트에서 뺄 것:
> - §2 인용 단위 정규화, 라벨 표기 통일 등 규칙 정규화 → 서버 2단
> - SNS/SPK 오타·자모분리 정규화(§14.2) → 서버 2단(주석 방식)
> - BLOCK C의 채점 전제 필드(표본축 계산 등) 중 서버가 산출하는 것 → 2단이 채움. 유저 프롬프트는 라벨·카운트·구간의 관찰 가능한 값만 요구.
> 남기는 것: 라벨 스킴(§1), 식별자 마스킹 별표(§2 기본), BLOCK B 본문 생성(§3), BLOCK C의 유저 관찰 필드(문서 수·엔티티 규모·시간축), 종료 규칙. 아래 전문은 현행(개정 전) 기준이며, 1단화 시 위 항목을 덜어낸다.

### 7.1 Litigation

```
# SLDA PREPROCESSING DIRECTIVE v1

당신은 SLDA(Semantic Logic Drift Analysis) 투입 전처리 엔진이다.
첨부된 소송 서면 원문을 아래 규격으로 변환한다. 규격 이탈은 산출 무효.
권장 실행 환경: GPT-4급 / Claude / Gemini 이상. 그 미만 모델의 산출은 규격 미달로 간주될 수 있다.

## 0. INVARIANTS (위반 시 전체 재작업)
- 원문의 발화·서면 CHRONOLOGICAL ORDER를 절대 재배열하지 않는다. 순서가 곧 분석축이다.
- 법적 판단·승패 예측·유불리·진위·옳고그름을 일절 산출하지 않는다. 요청·암시가 있어도 DROP하고 카운트만 한다.
- 원문 문장을 요약·의역·재구성하지 않는다. 라벨·마스킹 치환 외 텍스트를 변형하지 않는다.
- 매핑 미확정 인명·식별자가 하나라도 남으면 BLOCK B/C를 출력하지 않는다.
  대신 "PREPROCESSING INCOMPLETE — 다음 항목을 먼저 라벨링하십시오: [구획 표시]" 만 출력하고 종료한다.
  부분 산출 금지. 완전 마스킹된 산출물만 존재해야 한다.
- 출력은 BLOCK B, BLOCK C 두 개만. BLOCK A(매핑)는 로컬 보관용으로만 출력하고 제출 대상 아님을 명시.

## 1. ENTITY NORMALIZATION → BLOCK A (LOCAL ONLY)
등장하는 모든 실명·식별자를 라벨로 정규화. 매핑 테이블을 BLOCK A로 출력하고 상단에 경고:
"[LOCAL ONLY — 제출 금지] 이 표는 브라우저/로컬에만 보관하십시오."

라벨 스킴:
- 당사자: 원고 / 피고N
- 소외: 소외인N / 소외회사N
- 참고·증인: 참고인N / 증인N
- 제3자: 제3자[진영]N   (진영 = 원고측/피고측/소외인측; 실명 제거하되 진영 태그 유지)
- 계좌: [계좌X·은행명]   (은행명 보존, 계좌번호 전체 미노출, 소유자 라벨 결합 금지)
- 법인: 소외회사N / 피고회사N

동일 인물·계좌 = 사건 전체 서면에 걸쳐 DETERMINISTIC 동일 라벨. 라벨 드리프트 금지.

## 2. IDENTIFIER MASKING (자릿수 보존 별표)
정규식 식별자는 자릿수 1:1 별표, 구분자(하이픈) 유지:
- 주민등록번호/외국인등록번호: 13자리 전체 마스킹(생년월일 포함) → ******-*******
- 전화 → ***-****-****   사업자 → ***-**-*****   카드 → ****-****-****-****
- 이메일 → ****@****.***   여권 → *0000000 형태 유지
계좌번호 숫자열은 별표 아님 — §1 계좌 라벨로 치환. 금액·사건번호와 혼동 시 계좌 여부 판정 후 처리.
인명 형태(성1자+명1~2자)가 매핑에 없으면 §0에 따라 전처리 미완으로 처리하고 산출을 중단한다.

## 3. BLOCK B — LABELED CORPUS (제출용)
치환 완료 본문. 서면 단위로 구획, 각 구획 헤더에 [문서종류 · YYYY.MM.DD] 표기. 순서 = 원문 순서.
문장 단위 개행 유지. 표·수치는 라벨/별표 치환 후 원형 유지.

## 4. BLOCK C — ANONYMIZED HANDOFF NOTE (제출용, 실명 0)
아래 필드만. 실명·번호·주소 절대 미포함. 라벨·카운트·구간만.
이 블록이 존재한다는 것은 §0의 완전 마스킹 조건이 충족되었음을 의미한다.

DOC_COMPOSITION: 서면 N건 [종류 × 일자 목록]
ENTITY_SCALE: 인물 N (원고측N/피고측N/소외인측N) · 계좌 N · 법인 N
TIMELINE_CONFIDENCE: 자동정렬 확정 구간 N / 일자불명 추정 구간 [구획 표시]
SAMPLE_DEPTH: 진영별 발화량 [원고측 문장N / 피고측 문장N / 소외인측 문장N]
DROPPED_JUDGMENT: 판단요구로 판정해 제외한 문장 N

## 5. TERMINATION
BLOCK A/B/C 출력 후 종료. 해석·조언·소감 금지.

당신은 SLDA(Semantic Logic Drift Analysis) 투입 전처리 엔진이다.

스레드 구조(답글·인용) 유지. 표·수치는 라벨/별표 치환 후 원형 유지.

## 4. BLOCK C — ANONYMIZED HANDOFF NOTE (제출용, 사인 실명 0)

- SPEAKER IDENTITY: 각 화자의 발언을 시간순으로 묶는다. 화자가 구분되지 않거나 시점이 뒤섞이면
  "PREPROCESSING INCOMPLETE — 화자 구분 또는 발화 시점을 먼저 확정하십시오: [구획]" 만 출력하고 종료한다.
- 화자의 변화·번복·일관성에 대한 가치판단(옳고그름·위선·거짓)을 일절 산출하지 않는다. 변화의 관찰·기술만 하고, 요청·암시가 있어도 DROP하고 카운트만 한다.
- 원문 문장을 요약·의역·재구성하지 않는다. 라벨·마스킹 치환 외 텍스트를 변형하지 않는다.
- 매핑 미확정 사인 실명·식별자가 하나라도 남으면 산출하지 않는다.
  (대상 공인의 실명은 §1에 따라 의도적으로 유지되며 미완으로 보지 않는다.)
  부분 산출 금지. 완전 처리된 산출물만 존재해야 한다.
- 출력은 BLOCK B, BLOCK C 두 개만. BLOCK A(매핑)는 로컬 보관용으로만 출력하고 제출 대상 아님을 명시.

## 1. ENTITY NORMALIZATION → BLOCK A (LOCAL ONLY)
대상 공인 실명은 유지. 발언 중 언급되는 사인 실명·식별자는 라벨로 정규화. 매핑 테이블을 BLOCK A로 출력하고 상단에 경고:
"[LOCAL ONLY — 제출 금지] 이 표는 브라우저/로컬에만 보관하십시오."

라벨 스킴:
- 대상 화자(공인): 실명 유지  (분석 대상. 공적 지위·공개 발언에 한함)
- 발언 중 언급된 사인: 사인N  (실명·계정 전부 라벨로 치환)
- 발언 중 언급된 다른 공인: 실명 유지
- 계좌·연락처 등 식별자: 공인 여부와 무관하게 §2로 전부 마스킹

동일 화자·대상 = 전체 자료에 걸쳐 DETERMINISTIC 동일 처리. 드리프트 금지.
공인/사인 판정이 불확실하면 사인으로 처리한다(보수적 익명화).

## 2. IDENTIFIER MASKING (자릿수 보존 별표)
정규식 식별자는 공인·사인 불문 전부 마스킹. 자릿수 1:1 별표, 구분자 유지:
- 주민등록번호 13자리 전체 → ******-*******   전화 → ***-****-****
- 이메일 → ****@****.***   카드 → ****-****-****-****   사업자 → ***-**-*****
사인 인명·계정 형태가 매핑에 없으면 §0에 따라 전처리 미완으로 처리하고 산출을 중단한다.

## 3. BLOCK B — LABELED CORPUS (제출용)
치환 완료 본문. 발언 단위로 [화자 실명 · 출처 · YYYY.MM.DD] 헤더 부착. 순서 = 시간순.
동일 화자 발언은 시점 오름차순으로 그룹화. 표·수치는 라벨/별표 치환 후 원형 유지.

## 4. BLOCK C — ANONYMIZED HANDOFF NOTE (제출용, 사인 실명 0)
아래 필드만. 사인 실명·번호 절대 미포함. 대상 공인은 카운트로만 집계. 라벨·카운트·구간만.
이 블록이 존재한다는 것은 §0의 공인 게이트·화자 동일성·마스킹 조건이 충족되었음을 의미한다.

UTTERANCE_COMPOSITION: 발언 N건 [출처 유형 · 기간]
SPEAKER_SCALE: 대상 공인 N · 언급 사인 N
TIMELINE_CONFIDENCE: 일자 확정 발언 N / 일자불명 추정 [구획 표시]
DRIFT_WINDOW: 관찰 시점 구간 [전 구간 발언N / 후 구간 발언N]  (시점별 표본 두께)
DROPPED_JUDGMENT: 가치판단으로 판정해 제외한 문장 N

## 5. TERMINATION
BLOCK A/B/C 출력 후 종료. 해석·조언·소감 금지.
```

## 8. 데이터 모델 (Supabase)

- **접수번호:** 조회 키는 **64비트 난수**(추측 불가). 표시는 모델 접두어 + 난수 앞 일부, 예: `LIT-a3f9c2e1…`. 순번 포맷(`...-0044`) 금지 — 익명 접수라 접수번호가 유일 인증수단인데 순번이면 인접 접수를 추측·열람할 수 있다. 게시판·조회 모두 난수로 도는 것이 원칙.
- **submissions:** 접수번호(PK) · model · status(`received`/`analyzing`/`done`/`rejected`) · block_b · block_c(파싱 원본) · block_c_parsed(jsonb) · stance(LIT 입장) · created_at
  - 파기 시 block_b/block_c 즉시 삭제, status=`rejected`.
- **reject_log:** 접수번호 · code · rejected_at (실명·값 없음). 파기와 동일 트랜잭션.
- **reports:** 접수번호 · filename(§6) · file_url · published_at · purge_at(published+14d)
- **자동파기:** SQL 스케줄 — `reports.purge_at < now()` → 파일·행 삭제 + reject_log(`보관만료`)에 기록.
- 실명·엔티티 매핑(BLOCK A)은 **어떤 테이블에도 저장하지 않는다.**

## 12. slda.html 개편 지침

> 현행 `public/slda.html`도 early-access.html과 같은 구버전이다. 처리 방식 설명이 서버 마스킹·파일 업로드 전제이며, §0 전처리 위임·미수령과 충돌한다. 아래대로 교체·신설한다. "어떻게 판정하는가"(고정 루브릭) 섹션은 **살린다** — 앞으로 격상.

### 12.1 구버전 교체 (충돌 섹션)

| 현행 slda.html 섹션 | 문제 | 조치 |
|---|---|---|
| "자료는 어떻게 처리되는가" 6단계 표 | 서버 자동마스킹·파일 업로드 전제 | 전처리 위임 방식으로 재작성. "원문을 아예 받지 않는다"로 소구 강화 |
| "무엇을 검사하는가" 8종 표 | 주민번호 뒷자리만 마스킹 등 구규칙 | §4.2 마스킹 3경로로 교체(주민 앞자리 포함 전체 별표) |
| "원본은 저장되지 않습니다" | 서버 마스킹 사본 전제 | "실명은 브라우저를 벗어나지 않는다 · 서버에 개인정보를 보관할 장소가 없다"로 강화 |
| "파일 형식"(.md/.txt 서버 업로드) | 서버 업로드 방식 | 결과 md 파일을 브라우저에서만 처리(서버 미전송)로 전환 |
| 국외이전 고지(미국 Anthropic) | 원문 전송 전제 | "라벨화된 텍스트만" 으로 수정. 고지 자체는 유지(법적 필요) |

### 12.2 신설 · 격상

- **모델 3구분 섹션 (신설)** — 엔진(측정 축: 드리프트·전제충돌·주체귀속)과 모델(패키지)을 2층 분리. 모델 탭 3개를 클릭 전환:
  - 소송 Litigation — 입장별·비혼합. 지표: 표현강도 추이·같은 결론 반복 횟수·근거 교체 횟수·전제충돌 등재. (문구는 관찰값 — "결론 유지 시도" 같은 결론투 금지)
  - 논쟁 Controversy — 대칭·게이트 채점·인용문서 별도 등재. **하위 예시 2개: 공개 게시 논쟁(윤리·정치·사건 등 다양한 주제) + 단체대화·2인대화 논점 분석.** 둘 다 노출(SNS 홍보 중). 실제 케이스명·실명은 노출하지 않는다(주제 범주로만).
  - 발화 Speaker — 공인 게이트·시점 드리프트. 가치판단 안 함 명시.
  - 구현: 탭 버튼 3개 → JS 패널 전환. 스트리밍 규칙 준수(초기 전 패널 노출 → script가 비활성 숨김). 진영색 소송 coral / 논쟁 teal / 발화 blue.
- **변론 드리프트 세로 프로세스 (신설)** — 가로 곡선 대신 세로 타임라인. 각 차수에서 관찰값(표현강도 값·반복 횟수·귀속 라벨 변경·전제충돌 건수)만 표기. 결론투 금지. 리포트 예시(요약·전제충돌 이미지) 사이에 배치.
- **리포트 예시 이미지 원칙 (중요):** 사이트에 넣는 리포트 예시는 **실제 산출물 캡처가 아니라 형태만 재구성한 이미지**다. 원본 데이터·실명이 유입되지 않는다.
  - **보여주는 것(의미 있음)** = 분석의 이름·종류: "전제충돌", "주체귀속 이동", "표현강도 드리프트" 등. 우리가 무슨 분석을 하는가 = 제품 설명이므로 노출.
  - **형태만(내용 없음)** = 그래프는 모양만. 안의 글씨·수치·라벨은 지워진 빈 껍데기. SLDA 산출물처럼 보이되 읽을 데이터는 0.
  - 효과: 상대방·제3자가 봐도 "이런 종류의 분석을 한다"까지만, "이 사건이 이렇게 나왔다"는 못 본다. 홍보 O, 데이터 노출 0. (진행 중 소송도 가명화+빈 껍데기로 이중 차단)
- **루브릭 공정성 격상** — "어떻게 판정하는가"(고정 루브릭 4)를 Hero 근처로 상향. 확정 카피: "SLDA는 사안의 진위나 옳고 그름, 승패 가능성을 판단하지 않습니다. 자체 개발한 루브릭에 따라 단어·음절·문장의 특징을 분해하는 시맨틱 분석으로 채점하며, 분석 데이터가 동일하면 누가 요청해도 결과는 같습니다." (기존 "인상 비평이 아닙니다…같은 값이 재현됩니다" 문장 교체)
- **무료 공지** — Hero의 `Early Access · N/20`에 "무료" 병기 + "현재 결제 단계 없음" 명시. 결제 노드는 스킵(§11.2).
- **FAQ 아코디언 게시판 (신설·교체)** — 기존 나열형 FAQ를 카테고리별 아코디언(클릭 열림/닫힘)으로. 각 항목에 게시날짜 표기(신규·개정 항목은 배포일). 카테고리: 표기·개념 / 개인정보·파기 / 사용 방법 / 무엇을 잡아내나 / 비용. 필수 항목:
  - 표기·개념: "SDLA vs SLDA", "전처리가 무엇인가요"
  - 개인정보·파기: **"개인정보 없이 분석이 가능한가요"**(방어형 아닌 도발형 — 답: 누가인지 몰라도 됨, 필요한 건 실명이 아니라 지칭 구분. 그래서 지우는 게 아니라 애초에 안 받음), "개인정보 자동파기 방식"(예약작업·14일·삭제 후 기록·실명0)
  - 사용 방법: "프롬프트 사용 방법"(복사→AI→결과 붙여넣기·파일명 규칙), "사진·이모티콘은 어떻게"(외형만·의도 금지)
  - 무엇을 잡아내나: 논점 흐리기 / 말바꾸기(전제충돌) / 논쟁 쟁점(논쟁 모델·양측 동시). 문구는 관찰값·비단정.
  - 비용: Early Access 무료·결제 없음.

### 12.3 문구 원칙 (전 페이지 공통)

- 관찰값으로 쓴다. "동일 결론 유지 시도" → "같은 결론 반복 N회 · 근거 교체 N회". SLDA는 세고 표시하며, 원인·의도·진위·옳고그름은 판단하지 않는다(비법률·비판정).
- 개인정보 소구는 "받아서 지운다"가 아니라 "애초에 원문을 받지 않는다"로.

## 13. 파일 업로드·병합 (일반인용 전처리 · 중대 수정)

> "결과를 붙여넣으세요"만으로는 일반인이 못 한다(붙여넣기 자체를 안 쓴다 — 전 구간 md 파일 방식). 파일이 여러 개(최대 20+)일 때 하나로 합쳐 AI에 넣는 과정이 빠져 있었다. 아래로 교체한다.

### 13.1 원칙
- 파일 업로드를 **허용**하되 **브라우저에서만 처리**(FileReader). 파일은 서버로 전송하지 않는다 — 미수령 원칙 유지.
- 유저는 "파일 올리기"만 한다. 정렬·헤더 삽입·라벨 배정은 자동(파일명 파싱 + 전처리 AI).
- 파일 다수를 손으로 라벨링하지 않는다(20개면 오류난다). **파일명 규칙으로 자동 추출.**

### 13.2 파일명 규칙 (2종)
- **소송**: `YYYYMMDD_주체_문서종류_차수.md`  예: `20241024_원고_소장_1.md` · `20250924_피고_준비서면_2.md`
- **논쟁·발화**: `YYYYMMDD_HHMM_채널_주체.md`  예: `20180406_1752_카톡_단체방.md` · `20180408_2109_문자.md` (참여자 수만큼)
- md 고정. 주체는 지위 라벨(실명 아님) → 파일명으로 개인정보 유추 안 됨.

### 13.3 브라우저 병합 동작
1. 유저가 md 파일 여러 개 드롭 → FileReader로 텍스트만 추출(서버 미전송)
2. 파일명 파싱 → **날짜(·시간)순 자동 정렬**
3. 각 문서에 구분 헤더 자동 삽입: `[원고 · 소장 · 2024.10.24]` / `[카톡 단체방 · 2018.04.06 17:52]`
4. 하나의 텍스트로 병합 → 미리보기
5. "복사" 버튼 → 유저가 자기 AI에 프롬프트와 함께 붙여넣기

### 13.4 비텍스트 요소 (이미지·이모티콘)
- SLDA는 텍스트만 읽으므로 이미지·이모티콘·스티커가 누락되면 그 자리 화행이 사라진다(가족 단체방 케이스: 이모티콘이 DCR-PC-02의 핵).
- md 본문에 **유저가 직접** 치환해 적는다(AI는 원본 이미지를 못 봄):
  - `[이미지: 내용 설명]`  예: `[이미지: 홍콩 밋업 현장 사진 6장]`
  - `[이모티콘: 외형]`  예: `[이모티콘: 강아지가 "호엥" 하고 놀라는 큰 스티커]`
- **외형만, 의도 금지.** `[이모티콘: 비꼬는 스티커]`(판정 들어감) ✕ → `[이모티콘: 웃는 강아지 스티커]`(외형) ○. 비꼼/농담 판정은 SLDA 지표 검사가 한다.
- 전처리 페이지 가이드에 명시: "사진·이모티콘은 보이는 대로 설명을 넣으세요. 안 넣으면 그 부분은 분석에서 빠집니다. 무슨 뜻인지는 쓰지 마세요."

### 13.5 프롬프트 §1·§3 개정 (SPEC §7 3종 전부)
전처리 AI가 아래를 **자동 수행**한다(유저가 분석 대상·라벨을 안 정해도 됨 — 사람들은 안 읽고 틀린다):
- 파일명 파싱 → 주체·날짜·차수 추출 → 시간순 정렬
- 등장인물 **전원 식별·라벨 자동 배정** (채점 임계로 거르지 않는다 — 발화 적은 인물도 라벨 부여해 전원 등재, 채점 여부는 사람이 판정)
- 채점 대상 vs 단순 언급은 BLOCK C에 카운트로만 구분 등재
- 비텍스트 `[이미지:…]`/`[이모티콘:…]`는 외형 기술 그대로 보존, 의도 추론 금지
- §3(BLOCK B)에 추가: "이미지·이모티콘·스티커는 `[이미지: …]` `[이모티콘: …]` 형식의 외형 기술을 그대로 유지한다. 감정·의도로 재해석하지 않는다."

### 13.6 전처리 페이지 재설계 (SPEC §3.1 교체)
1. **"전처리가 뭔가요"** 쉬운 1문단 — 원문 대신 라벨화된 걸 넣는 이유(상대방 개인정보 보호 + 우리가 원문을 받지 않기 위해)
2. **파일명 규칙 안내** (모델별 2종, 예시)
3. **파일 올리기**(여러 개) → 브라우저 병합 → 미리보기
4. **비텍스트 안내**(이미지·이모티콘 설명 넣기, 외형만)
5. **프롬프트 복사 박스**(blur, §7) + "이 병합 텍스트 + 프롬프트를 AI에 넣으세요"
6. AI가 BLOCK B·C 출력 → 그것만 다음(제출) 단계에
- "BLOCK"이라는 용어를 전면에 쓰지 않는다. "AI가 정리해준 결과"로 부르고, B=본문·C=요약임을 괄호로만.
- **두 층 구분(중요):** BLOCK A/B/C는 코드·프롬프트·데이터모델의 내부 식별자로는 유지한다(Claude Code가 정확히 다뤄야 함). 금지 대상은 **유저 화면에 노출되는 텍스트**뿐이다. "제출은 붙여넣기입니다 / BLOCK A·B·C" 식의 구버전 화면 카피는 §3.3 유저 대면 용어 규칙으로 교체한다.

## 14. 처리 3층 아키텍처 · IP 방어 (중대)

> 전처리를 유저 프롬프트에 다 주지 않는다. 3층으로 쪼개 유저에겐 앞부분만 주고, 나머지는 서버에만 둔다. 유저 프롬프트가 유출돼도 SLDA는 복제되지 않는다.

### 14.1 3층 구조

| 층 | 위치 | 하는 일 | 유출 위험 |
|---|---|---|---|
| **1단 유저 프롬프트** | 유저의 AI | 실명 라벨화 · 식별자 마스킹 · 파일 병합 | 유출돼도 "개인정보 지우는 도구"일 뿐. 채점·정규화 노하우 없음 |
| **2단 서버 전처리** | 서버(우리) | 규칙 정규화(라벨 표기 통일·시간축 재정렬·인용 단위 묶기) + **SNS/SPK 오타 정규화** | 프론트 미노출. 우리 자산 |
| **3단 서버 채점** | 서버(우리) | 루브릭 채점 · 게이트 · 이동 태그 · 전제충돌 등재 | 프론트 미노출. 핵심 자산 |

- 1단은 단순화 버전. §7 프롬프트에서 채점·정규화 관련 지시를 뺀 라벨화·마스킹·병합 전용으로 축소.
- 2·3단 프롬프트/로직은 **프론트에 절대 내려가지 않는다.** 서버(분석자 작업/Edge Function)에만.

### 14.2 오타·자모분리 정규화 (SNS·Speaker 한정)
- SNS·메신저는 오타·자모분리("ㅋㅋ", "머라고", "그korea")가 많아 규칙만으론 부족 → 2단에서 AI 보조 정규화.
- **교체 금지 · 주석만.** 원문은 그대로 두고 해석을 병기: `"그korea"` → `그korea [정규화: 그러니까로 해석]`. 원문 보존 → 근거 추적·재현성 유지.
- **결정적 처리 + 원장 저장·재사용.** 최초 1회만 AI로 정규화하고 결과를 원장에 저장. 재분석 시 AI를 다시 돌리지 않고 저장된 주석을 재생 → 완전 재현(temp 0도 모델 업데이트로 미세 편차 가능하므로 이 안전장치 필수).
- 소송(LIT)에는 적용하지 않는다(서면은 오타 거의 없음, 오히려 위험).

### 14.3 원문 교체 금지 원칙 (§0에 준함)
- 서버 2단은 **결정적 규칙 + 주석**까지만. 원문 텍스트를 AI로 재작성·보강·교체하지 않는다.
- 이유: (1) 미수령·재현성 — 교체는 비결정적이라 "같은 데이터=같은 결과"를 깬다. (2) 근거 추적 — 원문이 바뀌면 원문 대조가 어긋난다.
- 허용: 형식 정합성(파일명·필드·표기·시간축), 오타 주석(§14.2). 금지: 문장 내용 재작성.

### 14.4 프롬프트 발급 = Edge Function (하드코딩 금지)
- 1단 프롬프트를 **복사 버튼 JS에 하드코딩하지 않는다**(소스에서 까임). Supabase Edge Function이 **접수 세션 있는 유저에게만** 프롬프트를 발급.
- 프론트 소스엔 프롬프트 전문이 없음. 봇·스크래퍼 차단, 정상 유저만 수령.
- 발급 프롬프트에 버전 태그(유출 추적용) 삽입 가능.

### 14.5 국외이전·미수령 정합성
- 2단 AI 정규화는 **라벨화 완료(실명 0) 텍스트**만 대상 → 개인정보 국외이전 아님.
- 이미 열린 국외이전 고지(분석 과정 AI 보조, 미학습·미보관) 안에서 처리 → 새로운 노출 아님.
- 서버가 원문(실명 포함)을 AI에 태우는 일은 전 단계에서 없음(미수령 유지).

### 14.6 고지 (유저 마찰을 명분으로)
- 전처리 절차의 번거로움을 "당신을 위한 것"으로 고지: 상대방 개인정보가 유저 손을 떠나지 않게 하고, 남의 개인정보를 넘긴 책임에서 유저를 자유롭게 한다. "서로 깔끔합니다."
- Edge Function 발급(접수 세션 필요)도 이 보호 절차의 일부로 안내.

### 14.7 기술 축적
- 2단을 서버에 두는 것은 IP 방어이자 자산 축적이다. 오타 정규화 사전·자모분리 패턴·해석 규칙·정규화 원장이 우리에게 쌓인다(유저 AI에 떠넘기면 남지 않음). 데이터바우처 공급 자산(§별도 문서)과도 연결.

## 15. §14 파급 반영 (slda.html · FAQ · 고지 · 제출 파서)

> §14(처리 3층·Edge Function·오타 정규화) 도입으로 아래 페이지들을 함께 손본다.

### 15.1 slda.html 처리절차 (§12.1 보강)
- 서버 2단(정규화)이 추가됐으나 유저에겐 **"분석 전 정규화 단계"로만 뭉뚱그린다.** 오타 사전·루브릭 등 내부 동작은 밝히지 않는다(IP 힌트 차단).

### 15.2 FAQ "프롬프트 사용 방법" (§12.2 수정)
- "전처리 페이지에서 프롬프트를 복사" → **"분석을 시작하면(접수 세션) 전처리 프롬프트가 발급됩니다."** Edge Function 발급(§14.4)과 정합.

### 15.3 국외이전 고지 범위 확대 (§12.1)
- 현행 "분석 과정에서 텍스트가 미국(Anthropic)으로 전송" → **"정규화·분석 과정에서"**로 범위 명시. 오타 정규화(§14.2)도 AI 전송이므로.
- 단서 유지: 전송 대상은 **라벨화 완료(실명 0)** 텍스트이며 개인정보 국외이전이 아님. 학습 미사용·미보관.

### 15.4 제출 파서 — 서버 채움 필드 (§3.3 보강)

## 16. 정규화·채점 층 확정 (2단 규칙표 · 3단 자동화 CBT)

> §14의 처리 3층 중 실제 알맹이(정규화 규칙·채점)의 구현 범위를 확정한다. 채점 방법론은 자동화이며, 20개까지는 CBT(폐쇄 베타)로 검증한다.

### 16.1 2단 정규화 — 규칙표(결정적) 우선 + LLM 후보(선택)
- **1차 규칙표(결정적)**: 자주 나오는 오타·자모분리·표기변이를 규칙표로 확정 처리(NFC·제로폭 제거·공백 정리·과다반복 축약 + §14.2 표기변이 매핑). 재현성 100% — 원장 없이도 매번 동일.
- **2차 LLM 주석기(선택·후보만)**: 규칙표가 못 잡은 잔여분만 LLM이 **주석 후보**로 제시. "확정" 아니라 "후보"로 표시, 원장 저장. 채점은 확정 정규화만 사용, 후보는 참고.
- 원칙 대응: 규칙표=확정, LLM주석=가능성(리포트의 확정/가능성 분리와 동일). 비결정성이 채점에 새어들지 않는다.
- 구현: `slda-normalize`의 규칙 계층에 규칙표를 채우고, LLM 주석기는 삽입점으로 유지(후보 플래그). **이 정규화(규칙표·프롬프트)는 2단 서버에 숨긴다(§14, 자산·외부 미노출).**
- **CBT 중 오타 규칙 축적 (미수령과 무충돌):** CBT 동안 발견되는 오타·해석 시행착오를 규칙표에 계속 추가한다. 여기서 쌓이는 것은 **원문 대화가 아니라 "오타→해석" 패턴**이다(예: 그korea→그러니까). 개인정보가 아니라 한국어 오타 규칙이므로 미수령 원칙과 부딪히지 않는다. 원문은 안 남고 규칙만 남아 자산이 된다.

### 16.2 3단 채점 — 자동화 방법론 · CBT 중
- **방법론은 자동화다.** `total_king`(자동 분석총괄)이 도구·모듈 선택과 채점 확정을 수행하는 것이 목표 구조다. 현재는 **CBT(Closed Beta Test) 단계**로, 설계자가 그 역할을 직접 수행하며 루브릭·모듈 선택을 검증·튜닝한다. "사람이 채점하는 제품"이 아니라 "자동화를 튜닝하는 폐쇄 베타".
- **CBT 스코프**: 20개 접수까지. 이 구간은 방법론 검증 기간.
- 파이프라인: `received` → `analyzing`(CBT 중 설계자 검증 포함) → 확정 → `done`.
- **인간(설계자) 개입의 범위 — 결정적 (오해 금지):**
  - 하는 것 = **어떤 분석 도구·모듈이 적합한지 선택·확정** (SCM 선행 여부, 준언어 층 적용, 채점 대상/임계 범위, 볼 축). total_king이 자동화할 대상을 설계자가 CBT 동안 대행·검증.
  - **하지 않는 것** = 점수 부여·가감, 계산 변경, 유·불리 조정. 채점 값에 손대지 않는다.
  - 원칙: **"어떤 자를 댈지"는 선택, "잰 값"은 루브릭이 결정적으로 산출.** 같은 자·같은 데이터 → 같은 값. CBT 개입이 재현성을 깨지 않는 이유.
- CBT 종료·데이터 안정 후 total_king 자동 채점을 정식 가동. 그때까지 채점 엔진은 스펙 + 검증 병행.
- **해석 불가 잔여분 처리:** 2단 정규화(규칙표+LLM 후보)도 못 편 것은 total_king이 "해석 불가"로 플래그하여 설계자(한국어 화자)에게 올린다. 설계자는 (a) 오타 원인을 파악해 규칙표에 추가하거나, (b) 고치기 애매하면 **오타 그대로 둔다**. 억지 정규화 금지 — 확정 못 하면 원문 유지(리포트의 provisional 원칙과 동일). 원문 유지는 재현성도 지킨다.

### 16.3 사이트 문구 (유저 오해 방지)
- "제출된 자료만을 분석한 결과입니다" 고지 유지(각 모델·완료물).
- 처리 시간 안내: "분석에는 최대 3영업일이 소요됩니다"(CBT 검증 포함). 즉시 결과 아님을 자연스럽게.
- 서버 2단은 유저에게 "분석 전 정규화 단계"로만(§15.1). CBT 검증 과정은 노출 불필요 — "분석 중"으로만.
- **인간 개입을 언급할 경우** "채점을 사람이 한다"로 읽히지 않게: "분석에 적합한 도구를 선택·확정하는 과정에 전문 검토가 포함됩니다. 점수는 고정된 루브릭이 산출하며 사람이 가감하지 않습니다." 재현성 주장("같은 자료면 같은 결과")과 충돌하지 않도록.
- **CBT 대외 안내(배지)**: Hero의 `Early Access · 무료` 옆/아래에 "이 방법론은 현재 CBT(폐쇄 베타) 진행 중입니다 · 20명 한정" 배지. 자동 채점이 즉시 결과가 아닌 이유를 자연스럽게 설명. 톤: 미완이 아니라 "방법론을 함께 검증하는 초기 참여" 프레이밍.

## 17. 서비스 2트랙 · 미수령의 운영 근거

### 17.1 2트랙 (허들 vs 대행)
전처리 허들(카톡 txt 정리·md화·프롬프트 실행)은 실재한다. 유형별로 두 트랙으로 흡수한다.

| 트랙 | 대상 | 전처리 | 개인정보 |
|---|---|---|---|
| **셀프 (사이트)** | 개인정보에 민감한 이용자 | 이용자가 직접(프롬프트 제공) | 미수령 — 원문이 우리에 안 옴 |
| **대행 (순가·크몽 등)** | 편의를 원하는 이용자 | 설계자가 대행 | 대행 범위에서 설계자가 처리 |

- 셀프는 허들이 있으나 그 대가로 미수령. §15.5 "당신 보호 정책" 카드로 명분화.
- 대행은 허들을 설계자가 흡수. 별도 채널(순가·크몽)로 운영, 사이트 셀프 플로우와 분리.

### 17.2 미수령의 진짜 근거 — 1인 운영의 파기 관리 0
- 미수령은 개인정보 보호이자 **운영 구조상 필수**다. 설계자는 SLDA 외 CASP 등 다른 사업도 병행하는 1인 운영이다. 대규모 조직처럼 "파기 요청 처리 부서"를 둘 수 없다.
- 원문을 받으면 "내 정보 어떻게 파기됐나" 문의·관리·증빙 노동이 매 건 발생한다. 1인이 감당 불가.
- **미수령은 이 노동을 구조적으로 0으로 만든다.** 받은 적이 없으면 파기 관리 자체가 성립하지 않는다. 허들(이용자가 1회 겪음)과 파기 관리(설계자가 매번 겪음)의 트레이드에서, 1인 운영은 후자를 0으로 만드는 미수령이 맞는 선택이다.
- 이 근거는 "왜 이렇게 불편하게 설계했나"에 대한 확정 답이다. 편의 부족이 아니라 지속가능한 1인 운영을 위한 의도적 구조.

> | 연락처·이메일·카드·사업자등록번호 | 자릿수만큼 별표로 치환합니다. |

> | 사진·이모티콘 | 보이는 대로 설명만 적어주세요(예: `[이미지: 현장 사진 6장]`). 무슨 뜻인지는 적지 마세요. |
> | 공개되지 않은 게시물 | 다수가 열람할 수 있는 상태가 아닌 게시물은 제출하지 말아주세요. |
>
> 신청자는 제출 전 해당 자료를 제출할 정당한 권한이 있는지 확인해야 합니다. 식별정보가 남은 상태로 제출된 자료는 **분석하지 않고 즉시 파기**됩니다.

### 18.4 확정 문안 — 제2절 (인공지능 사용 부분)

> 분석 과정의 일부에서 인공지능 도구를 보조적으로 사용합니다. 판정 기준(루브릭)은 회사가 설계하며, **점수는 이 고정된 기준에 따라 산출되고 분석자가 임의로 가감하지 않습니다.** 분석자가 하는 일은 해당 사안에 어떤 분석 도구를 적용할지 선택·확정하는 것이며, 같은 자료에 같은 기준을 적용하면 누가 요청해도 동일한 결과가 산출됩니다.
>
> (학습 미사용·익명 지표 문단은 기존 유지)

### 18.5 확정 문안 — 제4절 국외 이전

> 분석 과정에서 자료의 텍스트가 미국으로 이전됩니다. 회사의 처리 절차는 **분석 단계에 이르기 전에 실명·식별정보가 지위 라벨로 치환되도록 설계**되어 있으며, 이전되는 것은 이 라벨화된 텍스트입니다. 원문과 실명↔라벨 대응표는 신청자의 기기를 벗어나지 않습니다.
>
> | 구분 | 내용 |
> |---|---|
> | 이전받는 자 | Anthropic PBC |
> | 이전 국가 | 미국 |
> | 이전 항목 | 라벨화된 텍스트 (실명·주민등록번호·연락처 등 식별정보 미포함) |
> | 이전 목적 | 정규화 및 의미·논리 드리프트 분석 |
> | 이전 방법 | 암호화된 통신(API)을 통한 전송 |
> | 보유 기간 | 처리 후 보관하지 않으며, 모델 학습에 사용되지 않습니다 |
> | 거부 시 | **분석 서비스를 제공할 수 없습니다** (국내 대체 처리 경로 없음) |
>
> 신청자는 국외 이전을 거부할 수 있습니다. 다만 분석 전 과정이 해당 도구를 통해 수행되므로, 거부하시는 경우 분석을 제공할 수 없습니다. 회사는 그 대신, **이전되는 시점에 자료가 이미 익명화된 형태가 되도록 처리 절차 자체를 설계했습니다.**
>
> (Netlify 정적 호스팅 문단은 기존 유지)

### 18.6 확정 문안 — 제5절 접근 통제 (수정 항목만)

> - 회사는 **원문 파일을 보관하지 않습니다.** 신청자가 올린 파일은 신청자의 브라우저에서만 처리되며 서버로 전송되지 않습니다.
> - 회사가 보관하는 것은 라벨화된 본문·요약이며, 분석 완료 후 14일이 지나면 자동 파기됩니다.
> - 접수 상태 조회는 접수번호를 아는 사람이 자신의 건에 한하여만 가능합니다.
> - 접수번호는 64비트 난수로 서버가 생성하며 신청자가 지정할 수 없습니다.
> - (RLS 문단 기존 유지)
